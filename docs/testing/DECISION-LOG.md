# Testing Decision Log

The single source of truth for *why* the test suite is shaped the way it is. Code comments in the suite
state what the code does; every contestable choice — one a competent engineer could reasonably have made
differently — is recorded here instead, with the alternatives that were available, the reason the choice was
made, and the risk it carries.

A deviation from a literal reading of the requirements without a row in this table is a defect.

## Document coverage

| Area | Decisions recorded here |
|------|-------------------------|
| Frontend HTTP interception seam — `frontend/src/test-utils/handlers.ts` | §1, rows D1–D15 |

Rows are appended, never rewritten: a superseded decision gets a new row that names the row it replaces.

## §1 Frontend HTTP interception seam

Scope: `frontend/src/test-utils/handlers.ts`, the msw 1.x handler array the frontend Jest layer installs.
The measured behaviour these decisions are calibrated against was obtained by driving the assembled FastAPI
application through `TestClient(app, raise_server_exceptions=False)` with `app.db.firestore.get_db`
overridden, and by driving the frontend services through msw 1.3.5 under Jest 29 + jsdom. Both sets of
observations are reproduced in `docs/testing/TRACEABILITY-MATRIX.md` §A.

| # | Decision | Alternatives considered | Why this choice | Risks it carries |
|---|----------|-------------------------|-----------------|------------------|
| D1 | Ship **two separately named handler layers**: `frontendIsolationHandlers` (nominal success, test-only) and `currentBackendBehaviorHandlers()` (the statuses and bodies the backend returns today). | (a) One default array of nominal 200s — the shape before this decision. (b) Only current-behaviour handlers, no nominal layer. (c) A single array whose responses are switched by an environment flag. | (a) makes every future suite green against a synthetic success contract while appearing to cover integration: `GET /tweets/{id}` really answers 500, `POST /generate-response` really answers 404, and a nominal-only array erases both. (b) makes component rendering untestable, because three of the four routes never return usable data. (c) hides which contract a given test ran against inside global state. Two named layers make the choice explicit at each call site. | A suite author can still pick the isolation layer where a contract assertion was intended. Mitigated by naming (`frontendIsolation…` vs `currentBackendBehavior…`), by the module header table, and by the per-suite obligations in `TRACEABILITY-MATRIX.md` §A. |
| D2 | Keep `handlers` as an exported name, as an alias of `frontendIsolationHandlers`, rather than renaming it. | (a) Rename to `isolationHandlers` only. (b) Export the isolation array as the module default. | `frontend/TESTING.md` and `frontend/src/test-utils/msw-server.ts` are specified against the name `handlers`; renaming would break a contract fixed by a shipped onboarding document. Both names refer to one array, so there is no second source of truth. | Two names for one value invites the assumption that they differ. Mitigated by an assertion-grade doc comment on the alias and by both names appearing in the module header. |
| D3 | **Screen every request against its route contract inside the handler**, and answer a deviating request with a distinct non-success status instead of the nominal payload. | (a) Match on path only and answer 200 unconditionally. (b) Match on an exact query string in the msw pattern so a deviating request falls through to `onUnhandledRequest: 'error'`. (c) Assert the request only in each individual test. | (a) is the defect this row replaces: `limit=undefined`, an unknown query key, a placeholder path parameter and a wrongly keyed body were all answered 200. (b) breaks the real callers, whose query strings legitimately contain the literal string `undefined`, and would make `onUnhandledRequest` fire for correct traffic. (c) leaves every suite free to omit the assertion. Screening in the handler makes the request contract enforced once, for every suite. | A future caller shape that is legitimate but undocumented is rejected until its contract row is updated. That is the intended trade: an unexpected request must be visible. Each violation message names the exact field and value so the fix is mechanical. |
| D4 | Answer a screened-out request with **status 599** and a JSON body listing the violations. | (a) `res.networkError()`. (b) 400. (c) 500. (d) 422. | Neither FastAPI nor Starlette can emit 599, so the status can never be mistaken for a real backend outcome; 400, 422 and 500 are all statuses the real surface produces or could produce. `res.networkError()` destroys the response body, so the violation list would be unavailable to the failing test. | 599 is unfamiliar. Mitigated by `CONTRACT_VIOLATION_DETAIL` in the body, by the exported `CONTRACT_VIOLATION_STATUS` constant, and by the `console.error` in D5. |
| D5 | Also write the violations to `console.error`. | Rely on the 599 status alone. | `llmService.generateTweetResponse` catches the rejection and rethrows `Error('Failed to generate tweet response')`, and `twitterService` logs and rethrows, so a status alone can reach a test with the cause stripped. The log line carries the route id, the method, the full URL and every violation. | A suite that asserts an exact `console.error` call count sees the extra line. It is only emitted on a violation, which a conforming suite never triggers. |
| D6 | Record every intercepted request in a module-level log exposed through `recordedRequests()` / `lastRecordedRequest()`, and **auto-register `resetRecordedRequests` with `afterEach`** when the module loads inside a test run. | (a) No log; each suite spies on axios. (b) A log with an explicit reset the suites must remember to call. (c) A per-test `captureRequests()` scope helper. | The review requires exact assertions on the query, path and body a caller emitted; a log makes those assertions possible without mocking axios, which would mock the module under test. Explicit-reset-only (b) is an order-dependence hazard, and `setup-jest.ts` — where the `afterEach` would live — is not yet written, so the isolation guarantee cannot be delegated to it. (c) cannot observe requests issued from a component's mount effect. | Registering a hook as an import side effect is not obvious from a call site. Mitigated by the guard (`typeof afterEach === 'function'`), by the reset also being exported for explicit use, and by the operation being idempotent, so a later explicit `afterEach` is harmless. |
| D7 | Keep host-agnostic `*/…` patterns, but **restrict the origins a handler answers** to `http://localhost` and `http://127.0.0.1`, with `allowRequestOrigin()` as the documented opt-in. | (a) Answer any origin, as a bare wildcard does. (b) Pin the patterns to `http://localhost/undefined`. | The callers' base URL is the literal string `undefined`, so wildcard patterns are mandatory — but a bare wildcard also answers a request to a real host, which is exactly how a mistakenly configured base URL stays invisible. Pinning the pattern (b) would make the handlers stop matching the moment a suite sets a base URL, producing an unhandled-request failure whose message does not name the cause. An origin check answers with the violation instead. | A suite that intentionally points at an absolute URL must call `allowRequestOrigin` first. The failure it gets otherwise names the origin and the allow-list, so the remedy is in the message. |
| D8 | Model `GET /tweets` current behaviour with a **live coercion branch** — 200 when `skip` and `limit` coerce to `int`, otherwise 422 naming the failing parameter — rather than a fixed 422. | (a) A fixed 422 handler and a separate fixed 200 handler. (b) A fixed 200 handler only, with the 422 left to the backend integration suite. | The backend's answer depends on the request: `fetchTweets(2, 10)` really gets 200 and `getLatestTweets(5)` really gets 422, from the same route. A fixed status would force a suite to choose a handler per assertion and would misrepresent one of the two callers. The branch reproduces the observed rule — trim, then `^[+-]?\d+$` — so `limit=+7` and `limit=" 8 "` are 200 and `limit=undefined`, `limit=10.5` and `limit=` are 422, as measured. | The coercion rule is a reimplementation of pydantic v1's behaviour and could drift from it. Bounded by the fact that it governs a mock only; the authoritative assertions live in the backend integration suite, which exercises the real route. |
| D9 | Model `GET /tweets/{tweet_id}` and `POST /tweets/{tweet_id}/responses` as an **unconditional 500** with the plain-text body `Internal Server Error`, and provide **no handler for their 404 branch**. | (a) 404 when the id is unknown, 500 otherwise. (b) 200, matching the route's declared return type. | Both handlers read `Tweet.id`, which the pydantic model does not declare, so they raise before either `if not tweet` branch is reached: every id produces 500. A 404 handler would model a branch no request can reach and would invite a suite to assert behaviour the application cannot exhibit. | If the production defect is ever fixed, these handlers become wrong. They are named for the behaviour rather than the route, and `ROUTE_CONTRACTS` records the reachability finding, so the mismatch surfaces at the same time as the fix. |
| D10 | Register a handler for `POST */generate-response`, a path the backend does not route, and answer it **404 in the current-behaviour layer**. | (a) Omit the handler and let `onUnhandledRequest: 'error'` fire. (b) Omit it and add the endpoint to the backend. | `api.generateResponse` and `llmService.generateTweetResponse` both call this path, so without a handler neither service suite can run at all. (b) is forbidden: no product feature may be implemented. The 404 in the current-behaviour layer is the honest answer, and the nominal 200 in the isolation layer is what lets the service suites exercise the unwrapping of `data.generatedResponse`. | The nominal handler could read as evidence the endpoint exists. Mitigated by `backendContract: 'none - no router declares this path'` in the contract entry and by the mismatch rows in `TRACEABILITY-MATRIX.md`. |
| D11 | Register handlers for **exactly four routes** and no others — no `/users`, `/analytics`, `/config`, `/health`, `/api/trends` or `/api/config/twitter`, and no `rest.all('*')` catch-all. | (a) A catch-all returning 404 for everything unregistered. (b) Handlers for the empty routers, to document that they answer 404. | The four registered routes are the complete set that a module under `frontend/src/` requests. A catch-all would swallow every unexpected request and disable `onUnhandledRequest: 'error'`, which is the mechanism that makes an unmocked call fail loudly. The backend's 404 census belongs to the backend route-surface suite, where it is asserted against the real application. | A future frontend module that calls a fifth route fails with an unhandled-request error rather than a contract message. That is the intended signal, and the remedy is one contract entry plus one handler. |
| D12 | Serve tweet payloads built from `makeTweet()`, leaving `timestamp` to serialise to an **ISO-8601 string**, and export `makeDefaultTweetsJson()` as the value a suite asserts against. | (a) Pre-stringify the fixture. (b) Emit a value `tweetSchema` accepts. | The wire shape of a `datetime` is a string, and `frontend/src/schema/tweetSchema.ts` types `timestamp` as `z.date()`, so no raw JSON payload can satisfy that schema. Emitting a schema-satisfying value would hide the divergence; pre-stringifying would put a second tweet literal in the module. | A suite may expect `fetchTweets` to resolve to schema-valid objects. `makeDefaultTweetsJson` is the exported answer, and the `SerializedTweet` type states the difference in the type system. |
| D13 | Express the route contracts as **exported data** (`ROUTE_CONTRACTS`) that the screening runs on, rather than as prose beside the handlers. | (a) Prose comments only. (b) A separate Markdown table with no link to the code. | A description that the code does not execute drifts silently. Because the same `expectation` member drives the screening, a contract that no longer matches the handlers cannot go unnoticed, and a suite or an onboarding document can read the table directly. | The table mixes documentation fields with validation fields. The two groups are separated inside `RouteContract` and the validation half is a single named member. |
| D14 | Keep the isolation payload keys `generatedResponse` and `response` exactly as the callers read them. | Normalise both to one key. | `api.generateResponse` returns `response.data.generatedResponse` and the backend's responses route returns its text under `response`. The two keys differ in production; a mock that unified them would make a suite pass against a shape neither side produces. | None identified: the keys are asserted by the service suites and recorded in `TRACEABILITY-MATRIX.md`. |
| D15 | Fix none of the production defects this seam exposes — the ignored `page`, the missing `skip`, the `Tweet.id` access, the absent `/generate-response` route, the `undefined` base URL, the one-argument `fetchTweets` call. | Correct the defects so mock and backend agree. | The requirements permit exactly two production touches, neither of which covers any of these, and forbid implementing missing product features even where a test asserts one. The obligation is to assert current behaviour, not to normalise it. | The suite encodes defects, so fixing one later breaks tests. Every such test is enumerated in `TRACEABILITY-MATRIX.md` §A with the defect it pins, so the blast radius of a fix is known in advance. |
