# Testing Decision Log

The single source of truth for *why* the test suite is shaped the way it is. Code comments in the suite
state what the code does; every contestable choice — one a competent engineer could reasonably have made
differently — is recorded here instead, with the alternatives that were available, the reason the choice was
made, and the risk it carries.

A deviation from a literal reading of the requirements without a row in this table is a defect.

## Programme scope

Building this repository's first executable test suite: five layers — backend unit, backend integration,
frontend unit, frontend component and end-to-end — asserted against the code exactly as it exists rather
than as the design documents describe it, with exactly two pre-authorized production touches (§22) and no
other production change.

## How to read this log

Every decision is a table row with four columns: **Decision**, what was decided; **Alternatives
considered**, what else was genuinely on the table; **Why this choice**, the reason it won; and **Risks it
carries**, what it costs. No cell is ever left empty — a decision with no stated risk has not been thought
through. The leading `#` column is a stable citation handle, and roughly sixty test and configuration files
cite these ids from `@see` comments, so an id is never reused, renumbered or retired.

To add a decision: append a row to the section it belongs to, or open a new section if none fits, taking the
next unused id. Never edit a shipped row to change its meaning — append a new row that names the row it
supersedes or refines, and mark the superseded row in place. That convention is what keeps every citation in
the tree pointing at the reasoning that was current when it was written (D190).

The four user-specified rules are named wherever they bear on a decision, summarised rather than
transcribed; their full text lives in the project's rules document. **Rule 1 (Explainability)** is the rule
this file is the deliverable for. **Rule 2 (Observability)** is answered for the test system in §8, scoped
by C1, with its production gaps recorded in §23. **Rule 3 (Onboarding & Continued Development)** owns the
four onboarding documents, which project §23 as their suggested next tasks. **Rule 4 (Executive
Presentation)** owns the executive deck, which projects the risks column of every table below.

## §1 Frontend HTTP interception seam

Scope: `frontend/src/test-utils/handlers.ts`, the msw 1.x handler array the frontend Jest layer installs.
The measured behaviour these decisions are calibrated against was obtained by driving the assembled FastAPI
application through `TestClient(app, raise_server_exceptions=False)` — under both dependency dispositions,
with `app.db.firestore.get_db` left alone and with it overridden, and at both the path the client emits and the
path the backend declares — and by driving the frontend services through msw 1.3.5 under Jest 29 + jsdom. Both
sets of observations are reproduced in `docs/testing/TRACEABILITY-MATRIX.md` §A. Rows D1–D16 were taken against
the overridden disposition alone, which is what D169 and D170 correct.

## §22 The two authorized production touches, in full

Exactly two production changes were authorized, and both were required before the application object could
be constructed at all. This section carries their **complete** rationale, because the markers in the code
carry none: by C2 a `# TESTING:` comment names only the blocker it unblocks. Nothing below should be copied
back into those comments. The decision rows are D50, D51, D52 and D53; this is the argument behind them.

### Touch #1 — `backend/app/api/routes` becomes a package

`backend/app/api/routes` was a single extension-less **file** of 35 lines. Line 3 of `app/main.py` executes
`from app.api.routes import tweets, users, analytics, config`, which cannot resolve against a file, so
importing `app.main` failed with `ModuleNotFoundError: No module named 'app.api.routes'` and *no*
application-level test was possible — not a failing one, not a skipped one, none. The file is therefore
replaced by a package of four modules named for the four symbols that import statement asks for.

A byte-for-byte copy of the original body into `tweets.py` was impossible, because the original does not
compile. Two of its three endpoint signatures place a **defaulted parameter before a required one** — at
line 17, `def get_tweet(db: Session = Depends(get_db), tweet_id: str)`, and again at line 24,
`def generate_response(db: Session = Depends(get_db), tweet_id: str)`. CPython rejects this at parse time;
the exact wording of the message has changed across releases, so the defect is described here by its shape
rather than pinned to one string. The resolution is to reorder each signature to put the required parameter
first, giving `def get_tweet(tweet_id: str, db: Session = Depends(get_db))`, marked `# TESTING: param
order` at the two lines it applies to.

That reorder is **behaviour-preserving**, and the reason is specific rather than hopeful: FastAPI binds
dependencies and path parameters **by name**, not by position. It inspects the signature, matches
`tweet_id` to the `{tweet_id}` path segment and resolves `db` through `Depends(get_db)`, so parameter order
affects neither the runtime binding nor the generated OpenAPI schema. `get_tweets`, whose parameters were
already legal, is untouched.

`users.py`, `analytics.py` and `config.py` contain a `router = APIRouter()` and nothing else. **No endpoint
is created** in any of them, which matters because the legacy suite asserted against ten routes and the
requirements forbid implementing the nine that do not exist; each module carries a marker saying it
declares none, so an empty router is not mistaken for an invitation. No `__init__.py` is added, matching
the repository's existing PEP 420 convention throughout `backend/app/` (D50 alternative (c), and D185).

### Touch #2 — four `Settings` fields that production reads but never declared

Four attributes are read at runtime and declared nowhere, so each raised `AttributeError` on the path that
reads it: `configure_cors` reads `settings.ALLOWED_ORIGINS`, `create_access_token` reads
`settings.ALGORITHM`, `firestore.get_db` reads `settings.PROJECT_ID`, and both stream starters read
`settings.TWITTER_TRACK_KEYWORDS`. They are declared with least-privilege defaults:

```python
ALLOWED_ORIGINS: List[str] = []        # not ["*"] — the least permissive value that constructs
ALGORITHM: str = "HS256"
PROJECT_ID: str = ""                    # deliberately NOT an alias of GOOGLE_CLOUD_PROJECT
TWITTER_TRACK_KEYWORDS: List[str] = []
```

Two of these defaults are deliberately inconvenient, and a deployer must set them. An empty
`ALLOWED_ORIGINS` means CORS permits **no** origin until it is configured — strictly narrower than the
previous behaviour, which was to raise, so nothing that worked before stops working. An empty `PROJECT_ID`
fails loudly at the point of use rather than silently addressing whichever project `GOOGLE_CLOUD_PROJECT`
names, which is why aliasing the two was rejected: a wrong-project write is far worse than a clear error.

**No existing field name, type or default changed**, and no field was removed, so the settings contract the
requirements protect is intact. The touch stops at four fields: `TWITTER_CONSUMER_KEY` and
`TWITTER_CONSUMER_SECRET` are also read by production and also undeclared, but they are supplied from the
test side instead, keeping this touch to the four fields the requirements name (D52 alternative (c), D150).

## §23 The noted-but-not-fixed register

**None of the items below is fixed by this change set, and that is deliberate on three separate grounds.**
The minimal-change clause permits no production refactoring beyond what testability strictly requires; the
allow-list authorizes exactly two production touches (§22) and no third; and implementing a missing product
feature is forbidden outright, *even where an existing test asserted it*. Several of these are consequently
**pinned by assertions** rather than repaired — the suite asserts today's defective behaviour, so a future
fix will turn a passing test red on purpose, and `./TRACEABILITY-MATRIX.md` records which test pins which
defect so the blast radius of a fix is known before it is attempted.

This register is the source for the "suggested next tasks" section that Rule 3 (Onboarding & Continued
Development) requires of `../../backend/tests/README.md`, `../../frontend/TESTING.md`,
`../../e2e/README.md` and the additive Testing section of `../../README.md`. Each line is written to be
liftable on its own. Items are grouped by area, and every line names the file it concerns.

### Named in the requirements

- Routes issue SQLAlchemy `Session` type hints and `db.query(...)` calls against a Firestore-backed `get_db` dependency — two incompatible data-access models in one call path.
- Five frontend runtime dependencies were imported by the source but declared in no manifest at the frozen baseline: `react-router-dom`, `@reduxjs/toolkit`, `react-redux`, `zod`, `dayjs`.
- `README.md` describes an unrelated static-analysis product; the stale identity is left byte-for-byte intact by C3.
- The port triangle: `README.md` line 81 directs users to `http://localhost:8000`, `docker-compose.yml` maps `80:80` for the frontend (line 9) and `5000:5000` for the backend (line 27), and `nginx.conf` listens on 80 (line 13) and 443 (line 22). No two agree.

### Configuration and settings

- `app/db/bigquery.py` reads `Settings.GOOGLE_CLOUD_PROJECT` as a **class** attribute in two places, which pydantic v1 can never resolve because it strips declared fields from the class namespace.
- `settings.openai_engine` is read in lowercase while `case_sensitive = True` (`app/core/config.py` line 30), so it can never resolve.
- `settings.TWITTER_CONSUMER_KEY` and `settings.TWITTER_CONSUMER_SECRET` are read, but the declared fields are `TWITTER_API_KEY` and `TWITTER_API_SECRET`.
- `DOUBT_RATING_THRESHOLD = 0.7` (line 20) is referenced by **no production code anywhere**, so the doubt-rating gate the requirements describe does not exist; the constant is asserted, the gate is recorded as absent.
- `create_access_token` hardcodes a 15-minute expiry and ignores `ACCESS_TOKEN_EXPIRE_MINUTES = 30` (line 8).
- `API_V1_STR = "/api/v1"` (line 6) is declared, but no route is prefixed with it.

### Backend behaviour

- `app/db/firestore.py` has no `add_response`, although `app/tasks/response_generator.py` imports it.
- `response_generator.generate_response` awaits the synchronous `firestore.get_tweet`, so it fails on awaiting a `dict`.
- `process_pending_responses` calls `get_tweet(response_status="pending")` against a signature that takes one positional parameter.
- `twitter_service.start_twitter_stream` references `tweepy.Stream` without the module importing `tweepy`, so it always raises `NameError` — the function is dead code that can never complete.
- `TweetStreamListener.on_status` builds a `Tweet` from seven field names the schema does not declare, so every tweet that passes the popularity gate produces an eight-error `ValidationError` instead of a write.
- `GET /tweets/{tweet_id}` filters on `Tweet.id`, which the pydantic model does not have, so it returns HTTP 500 and its own 404 branch is unreachable.
- No implemented endpoint accepts a request body, so the real surface has no 422 path at all.
- Analytics SQL is assembled by f-string interpolation of caller-supplied date strings — an injection exposure as well as a validation gap; characterised by assertions under D162, not repaired.
- Inverted and malformed date ranges are accepted without validation and interpolated verbatim into the query.
- One of the ten routes the legacy suite asserted is implemented: there is no `/users`, `/analytics`, `/config`, `/token` or `/health` router, and the requirements forbid adding them.

### Frontend behaviour

- `src/store/index.ts` imports `{ tweetReducer }` and `{ configReducer }`, which the slices never export; the store silently has no valid reducer, Redux logs an invalid-reducer error, and `getState()` returns `{}`.
- `useAppDispatch` and `useAppSelector` are imported by three page modules and exported by nothing.
- `TweetCard` is imported by two components — `TweetManagement` imports it **from itself** — and is defined nowhere, so any non-empty tweet list renders an invalid-element-type error.
- `src/services/twitterService.ts` imports `getTweets`, which is not exported, and calls the two-parameter `fetchTweets` with a single argument.
- `src/services/api.ts` exports neither `api` nor `setupInterceptors`, both of which `src/app.tsx` imports.
- `src/store/configSlice.ts` imports a nonexistent `../schema/configSchema`, and the `Analytics` and `Configuration` components import service modules that do not exist.
- The axios base URL evaluates to the literal string `"undefined"`, so every request is issued to `undefined/tweets?...` — which is why the mock layer must match that base explicitly (D169).
- `formatNumber(1234.5678)` returns `'1,234.5,678'`: the grouping regex mangles the decimal part.
- `tweetSlice.updateTweet` compares `tweet.id === action.payload.id` on a shape that has no `id`, so `undefined === undefined` always matches and it overwrites index 0 regardless of which tweet was intended.
- `tweetSchema` types `timestamp` as `z.date()`, which no raw JSON payload can ever satisfy.
- `Analytics` imports the tree-shakeable `{ Chart }` and never calls `Chart.register`, so chart construction fails in every environment including a real browser (D92).
- `src/index.tsx` calls `ReactDOM.render`, a React 17 API, under React 18.
- All four `src/pages/*.tsx` modules are orphaned: `src/app.tsx` routes only to `src/components/*`, so no route reaches a page module.
