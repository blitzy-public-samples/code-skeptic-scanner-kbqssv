# Testing Decision Log

The single source of truth for *why* the test suite is shaped the way it is. Code comments in the suite
state what the code does; every contestable choice — one a competent engineer could reasonably have made
differently — is recorded here instead, with the alternatives that were available, the reason the choice was
made, and the risk it carries.

A deviation from a literal reading of the requirements without a row in this table is a defect.

## §1 Frontend HTTP interception seam

Scope: `frontend/src/test-utils/handlers.ts`, the msw 1.x handler array the frontend Jest layer installs.
The measured behaviour these decisions are calibrated against was obtained by driving the assembled FastAPI
application through `TestClient(app, raise_server_exceptions=False)` with `app.db.firestore.get_db`
overridden, and by driving the frontend services through msw 1.3.5 under Jest 29 + jsdom. Both sets of
observations are reproduced in `docs/testing/TRACEABILITY-MATRIX.md` §A.

| # | Decision | Alternatives considered | Why this choice | Risks it carries |
|---|----------|-------------------------|-----------------|------------------|
| D1 | Ship **two separately named handler layers**: `frontendIsolationHandlers` (nominal success, test-only) and `currentBackendBehaviorHandlers()` (the statuses and bodies the backend returns today). | (a) One default array of nominal 200s — the shape before this decision. (b) Only current-behaviour handlers, no nominal layer. (c) A single array whose responses are switched by an environment flag. | (a) makes every future suite green against a synthetic success contract while appearing to cover integration: `GET /tweets/{id}` really answers 500, `POST /generate-response` really answers 404, and a nominal-only array erases both. (b) makes component rendering untestable, because three of the four routes never return usable data. (c) hides which contract a given test ran against inside global state. Two named layers make the choice explicit at each call site. | A suite author can still pick the isolation layer where a contract assertion was intended. Mitigated by naming (`frontendIsolation…` vs `currentBackendBehavior…`), by the module header table, and by the per-suite obligations in `TRACEABILITY-MATRIX.md` §A. |
| D2 | Keep `handlers` as an exported name, as an alias of `frontendIsolationHandlers`, rather than renaming it. | (a) Rename to `isolationHandlers` only. (b) Export the isolation array as the module default. | `frontend/TESTING.md` and `frontend/src/test-utils/msw-server.ts` are specified against the name `handlers`; renaming would break a contract fixed by a shipped onboarding document. Both names refer to one array, so there is no second source of truth. | Two names for one value invites the assumption that they differ. Mitigated by an assertion-grade doc comment on the alias and by both names appearing in the module header. |
| D3 | **Screen every request against its route contract inside the handler**, and answer a deviating request with a distinct non-success status instead of the nominal payload. | (a) Match on path only and answer 200 unconditionally. (b) Match on an exact query string in the msw pattern so a deviating request falls through to `onUnhandledRequest: 'error'`. (c) Assert the request only in each individual test. | (a) is the defect this row replaces: `limit=undefined`, an unknown query key, a placeholder path parameter and a wrongly keyed body were all answered 200. (b) breaks the real callers, whose query strings legitimately contain the literal string `undefined`, and would make `onUnhandledRequest` fire for correct traffic. (c) leaves every suite free to omit the assertion. Screening in the handler makes the request contract enforced once, for every suite. | A future caller shape that is legitimate but undocumented is rejected until its contract row is updated. That is the intended trade: an unexpected request must be visible. Each violation message names the exact field and value so the fix is mechanical. |
| D4 | Answer a screened-out request with **status 599** and a JSON body listing the violations. | (a) `res.networkError()`. (b) 400. (c) 500. (d) 422. | Neither FastAPI nor Starlette can emit 599, so the status can never be mistaken for a real backend outcome; 400, 422 and 500 are all statuses the real surface produces or could produce. `res.networkError()` destroys the response body, so the violation list would be unavailable to the failing test. | 599 is unfamiliar. Mitigated by `CONTRACT_VIOLATION_DETAIL` in the body, by the exported `CONTRACT_VIOLATION_STATUS` constant, and by the `console.error` in D5. |
| D5 | Also write the violations to `console.error`. | Rely on the 599 status alone. | `llmService.generateTweetResponse` catches the rejection and rethrows `Error('Failed to generate tweet response')`, and `twitterService` logs and rethrows, so a status alone can reach a test with the cause stripped. The log line carries the route id, the method, the full URL and every violation. | A suite that asserts an exact `console.error` call count sees the extra line. It is only emitted on a violation, which a conforming suite never triggers. |
| D6 | Record every intercepted request in a module-level log exposed through `recordedRequests()` / `lastRecordedRequest()`, and **auto-register `resetRecordedRequests` with `afterEach`** when the module loads inside a test run. | (a) No log; each suite spies on axios. (b) A log with an explicit reset the suites must remember to call. (c) A per-test `captureRequests()` scope helper. | The review requires exact assertions on the query, path and body a caller emitted; a log makes those assertions possible without mocking axios, which would mock the module under test. Explicit-reset-only (b) is an order-dependence hazard, and `setup-jest.ts` — where the `afterEach` would live — is not yet written, so the isolation guarantee cannot be delegated to it. (c) cannot observe requests issued from a component's mount effect. | Registering a hook as an import side effect is not obvious from a call site. Mitigated by the guard (`typeof afterEach === 'function'`), by the reset also being exported for explicit use, and by the operation being idempotent, so a later explicit `afterEach` is harmless. |
| D7 | **[Superseded by D103, and again by D136 — the wording below is the decision as originally taken, not the shipped behaviour.]** Keep host-agnostic `*/…` patterns, but **restrict the origins a handler answers** to `http://localhost` and `http://127.0.0.1`, with `allowRequestOrigin()` as the documented opt-in. | (a) Answer any origin, as a bare wildcard does. (b) Pin the patterns to `http://localhost/undefined`. | The callers' base URL is the literal string `undefined`, so wildcard patterns are mandatory — but a bare wildcard also answers a request to a real host, which is exactly how a mistakenly configured base URL stays invisible. Pinning the pattern (b) would make the handlers stop matching the moment a suite sets a base URL, producing an unhandled-request failure whose message does not name the cause. An origin check answers with the violation instead. | A suite that intentionally points at an absolute URL must call `allowRequestOrigin` first. The failure it gets otherwise names the origin and the allow-list, so the remedy is in the message. |
| D8 | **[Refined by D137 — the branch below is correct, but it is the **dependency-overridden** disposition, not what the unoverridden application returns.]** Model `GET /tweets` current behaviour with a **live coercion branch** — 200 when `skip` and `limit` coerce to `int`, otherwise 422 naming the failing parameter — rather than a fixed 422. | (a) A fixed 422 handler and a separate fixed 200 handler. (b) A fixed 200 handler only, with the 422 left to the backend integration suite. | The backend's answer depends on the request: `fetchTweets(2, 10)` really gets 200 and `getLatestTweets(5)` really gets 422, from the same route. A fixed status would force a suite to choose a handler per assertion and would misrepresent one of the two callers. The branch reproduces the observed rule — trim, then `^[+-]?\d+$` — so `limit=+7` and `limit=" 8 "` are 200 and `limit=undefined`, `limit=10.5` and `limit=` are 422, as measured. | The coercion rule is a reimplementation of pydantic v1's behaviour and could drift from it. Bounded by the fact that it governs a mock only; the authoritative assertions live in the backend integration suite, which exercises the real route. |
| D9 | Model `GET /tweets/{tweet_id}` and `POST /tweets/{tweet_id}/responses` as an **unconditional 500** with the plain-text body `Internal Server Error`, and provide **no handler for their 404 branch**. | (a) 404 when the id is unknown, 500 otherwise. (b) 200, matching the route's declared return type. | Both handlers read `Tweet.id`, which the pydantic model does not declare, so they raise before either `if not tweet` branch is reached: every id produces 500. A 404 handler would model a branch no request can reach and would invite a suite to assert behaviour the application cannot exhibit. | If the production defect is ever fixed, these handlers become wrong. They are named for the behaviour rather than the route, and `ROUTE_CONTRACTS` records the reachability finding, so the mismatch surfaces at the same time as the fix. |
| D10 | Register a handler for `POST */generate-response`, a path the backend does not route, and answer it **404 in the current-behaviour layer**. | (a) Omit the handler and let `onUnhandledRequest: 'error'` fire. (b) Omit it and add the endpoint to the backend. | `api.generateResponse` and `llmService.generateTweetResponse` both call this path, so without a handler neither service suite can run at all. (b) is forbidden: no product feature may be implemented. The 404 in the current-behaviour layer is the honest answer, and the nominal 200 in the isolation layer is what lets the service suites exercise the unwrapping of `data.generatedResponse`. | The nominal handler could read as evidence the endpoint exists. Mitigated by `backendContract: 'none - no router declares this path'` in the contract entry and by the mismatch rows in `TRACEABILITY-MATRIX.md`. |
| D11 | Register handlers for **exactly four routes** and no others — no `/users`, `/analytics`, `/config`, `/health`, `/api/trends` or `/api/config/twitter`, and no `rest.all('*')` catch-all. | (a) A catch-all returning 404 for everything unregistered. (b) Handlers for the empty routers, to document that they answer 404. | The four registered routes are the complete set that a module under `frontend/src/` requests. A catch-all would swallow every unexpected request and disable `onUnhandledRequest: 'error'`, which is the mechanism that makes an unmocked call fail loudly. The backend's 404 census belongs to the backend route-surface suite, where it is asserted against the real application. | A future frontend module that calls a fifth route fails with an unhandled-request error rather than a contract message. That is the intended signal, and the remedy is one contract entry plus one handler. |
| D12 | Serve tweet payloads built from `makeTweet()`, leaving `timestamp` to serialise to an **ISO-8601 string**, and export `makeDefaultTweetsJson()` as the value a suite asserts against. | (a) Pre-stringify the fixture. (b) Emit a value `tweetSchema` accepts. | The wire shape of a `datetime` is a string, and `frontend/src/schema/tweetSchema.ts` types `timestamp` as `z.date()`, so no raw JSON payload can satisfy that schema. Emitting a schema-satisfying value would hide the divergence; pre-stringifying would put a second tweet literal in the module. | A suite may expect `fetchTweets` to resolve to schema-valid objects. `makeDefaultTweetsJson` is the exported answer, and the `SerializedTweet` type states the difference in the type system. |
| D13 | Express the route contracts as **exported data** (`ROUTE_CONTRACTS`) that the screening runs on, rather than as prose beside the handlers. | (a) Prose comments only. (b) A separate Markdown table with no link to the code. | A description that the code does not execute drifts silently. Because the same `expectation` member drives the screening, a contract that no longer matches the handlers cannot go unnoticed, and a suite or an onboarding document can read the table directly. | The table mixes documentation fields with validation fields. The two groups are separated inside `RouteContract` and the validation half is a single named member. |
| D14 | Keep the isolation payload keys `generatedResponse` and `response` exactly as the callers read them. | Normalise both to one key. | `api.generateResponse` returns `response.data.generatedResponse` and the backend's responses route returns its text under `response`. The two keys differ in production; a mock that unified them would make a suite pass against a shape neither side produces. | None identified: the keys are asserted by the service suites and recorded in `TRACEABILITY-MATRIX.md`. |
| D15 | Fix none of the production defects this seam exposes — the ignored `page`, the missing `skip`, the `Tweet.id` access, the absent `/generate-response` route, the `undefined` base URL, the one-argument `fetchTweets` call. | Correct the defects so mock and backend agree. | The requirements permit exactly two production touches, neither of which covers any of these, and forbid implementing missing product features even where a test asserts one. The obligation is to assert current behaviour, not to normalise it. | The suite encodes defects, so fixing one later breaks tests. Every such test is enumerated in `TRACEABILITY-MATRIX.md` §A with the defect it pins, so the blast radius of a fix is known in advance. |
| D16 | **Supersedes D6. [The one-owner decision stands; the call list below is the list as of this row. D136 removed `resetAllowedRequestOrigins()` with the mutable allow-list, and the shipped hook now calls `assertNoIsolationViolations()`, then `server.resetHandlers()`, `resetHandlerState()` and a delete of `REACT_APP_API_BASE_URL`.]** Move all per-test cleanup of this module's mutable state into `src/test-utils/setup-jest.ts`, whose `afterEach` calls `server.resetHandlers()`, `resetAllowedRequestOrigins()` and `resetRecordedRequests()`. `handlers.ts` registers no Jest hook at all. | (a) Keep D6's import-time `afterEach` registration and add a second one for the origin set. (b) Leave both resets to each suite. (c) A single exported `resetHandlerState()` that suites call. | D6 registered its hook as an import side effect only because `setup-jest.ts` did not exist yet; it now does, and it is loaded once per test file through `setupFilesAfterEnv`. Two owners of one lifecycle is how the origin allow-list came to have an exported reset that nothing called: an origin added by one test survived into every later test in the file. (b) and (c) leave the guarantee to author discipline. One owner, three resets, no hook hidden in an import. | A suite that runs without `setup-jest.ts` — a hand-rolled Jest invocation with a different config — gets no reset at all. Bounded by the config being the only supported entry point, and by every reset staying exported for explicit use. |

## §2 Backend test infrastructure

Scope: `backend/pytest.ini`, `backend/tests/conftest.py`, `backend/tests/integration/conftest.py`,
`backend/tests/factories.py`. Every behaviour these decisions are calibrated against was obtained by
executing the code on CPython 3.9.25 with the pinned stack in `backend/requirements-dev.txt`.

| # | Decision | Alternatives considered | Why this choice | Risks it carries |
|---|----------|-------------------------|-----------------|------------------|
| D20 | Seed the eight required `Settings` fields, install the `Optional` shim and neutralise ambient Google credentials at **`conftest.py` module scope**, and import no `app.*` module there. | (a) An `autouse` fixture. (b) `env` entries via a pytest plugin such as `pytest-env`. (c) A committed `.env` file. | `app/core/config.py` runs `settings = Settings()` at import and seven further modules build their own `Settings()` the same way, so the values must exist before *collection* imports any test module — an `autouse` fixture runs far too late. (b) adds a dependency for one assignment loop. (c) puts test values in a file the application would also read. | Module-scope side effects are invisible from a test body. Bounded by `os.environ.setdefault`, so a deliberately exported value still wins, and by the module docstring naming every effect. |
| D21 | Expose the five missing-symbol shims (`Optional`, `verify_token`, `TwitterService`, `LLMService`, `add_response`) **only** as conftest fixtures, and give each of the four class/function shims a fresh object per test. | (a) Each suite installs its own with `patch`. (b) One session-scoped shim set. (c) Create the missing symbols in production. | (a) is how the same shim ends up spelled three different ways; (b) shares call bookkeeping between tests, so a count assertion depends on execution order; (c) implements missing product features, which the requirements forbid. A fixture per shim makes the substitution a declared dependency of each test. | A test that needs a shim and forgets the fixture fails with `AttributeError`/`NameError` rather than a message naming the shim. That is the intended signal: production fails the same way. |
| D22 | Install every shim on the **source module and on each consumer that binds it with `from … import …`**, and unbind it from all of them on teardown, driven by the `MISSING_SYMBOL_CONSUMERS` table. | (a) Patch the source module only. (b) Evict and re-import every consumer per test. (c) Patch each consumer inside the suites that need it. | (a) leaves `app.api.dependencies.verify_token`, `app.api.routes.tweets.LLMService` and `app.tasks.tweet_processor.LLMService` pointing at whichever object they captured first, so a later test passes against a leftover and a fixture-less test passes at all. (b) cannot be applied to `app.main` or the tweets router without breaking the `dependency_overrides` identity match and stacking a second CORS middleware (D23). (c) duplicates the boundary knowledge in every suite. | The table has to be kept in step with production imports. Bounded by the shims being *deleted* on teardown, which turns a stale table entry into an immediate failure rather than a silent pass. |
| D23 | Keep `app.main`, `app.api.routes.tweets`, `app.core.config`, `app.db.firestore` and `app.schema.tweet` **cached for the session**, and evict only `app.tasks.response_generator`. | (a) Reload every module per test. (b) Reload nothing, including `response_generator`. | `app.dependency_overrides` is keyed on the `get_db` object the router captured in its three `Depends(get_db)` defaults, so re-importing the router breaks every override; re-importing `app.core.config` creates a second `Settings` singleton; re-importing `app.main` stacks a second CORS middleware and a second copy of each router. `response_generator` runs `llm_service = LLMService()` at module scope, so it is the one module whose state genuinely has to be rebuilt. | Session-cached modules accumulate whatever a test does to them. Mitigated by D22, which is what makes the caching safe. |
| D24 | Import `app.main` and `app.api.dependencies` **early**, through `_import_get_db_consumers`, before any fixture replaces `app.db.firestore.get_db`. | (a) Let each fixture import them in whatever order it needs. (b) Key `dependency_overrides` on a re-read of `firestore.get_db`. | The router's `Depends(get_db)` defaults hold the function object present at *its* import time. If a fixture patched `get_db` first, the router would capture the mock and no override would ever match. (b) is the same bug from the other side. | An ordering rule enforced by a helper rather than by the type system. Bounded by the helper being idempotent and called from every fixture that patches `get_db`. |
| D25 | Permit a loopback connect **only to a port this process bound**, recording ports by wrapping `socket.socket.bind`/`listen`, and refuse non-loopback `getaddrinfo`/`gethostbyname`. | (a) Allow all loopback traffic, which is what the guard did before. (b) Block loopback entirely. (c) Block only `socket.socket.connect`, leaving resolution alone. | This host is shared between concurrent clones, so loopback also reaches a sibling's dev server or database — allowing it by address makes an accidental cross-clone dependency invisible. (b) breaks the asyncio `ProactorEventLoop` self-pipe and the starlette `TestClient` portal, both of which connect to a port they bound in-process through `socket.socketpair`. (c) lets a lookup of a real host leave the box before any connect is attempted. | Defense in depth, not a guarantee: a module that captured `socket.getaddrinfo` before the fixture ran keeps its own reference, and a C-level socket that never passes through `socket.socket` is not covered — which is exactly why the gRPC channel factories are blocked separately. |
| D26 | Block the gRPC channel factories by name (`grpc`, `grpc.aio`, `google.api_core.grpc_helpers[_async]`) in addition to the socket guard. | (a) Rely on the socket guard. (b) Uninstall the Google client libraries in the test environment. | `google-cloud-firestore` opens its transport in the gRPC C core, which never passes through `socket.socket`: an unpatched `get_tweet` reached Google Cloud for real and returned `NotFound: 404 The database (default) does not exist`. (b) would make the modules unimportable and the suite unable to assert their current behaviour. | The target list is version-specific. Bounded by each target being skipped when absent, so a version without one of them still runs. |
| D27 | Neutralise `google.auth.default` with a stand-in that **returns** a fake credential pair rather than raising. | (a) Let `DefaultCredentialsError` propagate from an absent key file. (b) Set `GOOGLE_APPLICATION_CREDENTIALS` to a fake key file on disk. | A raising stand-in turns every unmocked data-access path into a credential error, which hides *which* boundary was left unpatched. Returning a credential lets the call proceed to the transport, where D25/D26 name the exact target. (b) puts a credential-shaped file in the repository. | A test could mistake the fake pair for real resolution. Bounded by `GOOGLE_APPLICATION_CREDENTIALS` pointing at a path that never exists, so even a bypass reads nothing. |
| D28 | Build the `TestClient`s **without** entering them as context managers, and `close()` them on teardown. | (a) `with TestClient(app) as client:`. (b) Construct and never close. (c) Patch the startup and shutdown handlers, then use the context manager. | The startup handler calls `get_db()` and then `await start_tweet_stream()`, which blocks on a live Twitter stream — so the lifespan must not run, while the handlers must stay *registered* for the lifecycle suite to assert. (b) leaks an `httpx` transport per test. (c) asserts against handlers the test itself replaced. | The startup and shutdown bodies are never executed by any test. Recorded as a coverage ceiling in `TRACEABILITY-MATRIX.md` rather than closed. |
| D29 | Give every factory in `backend/tests/factories.py` an `**overrides` parameter and build a fresh mutable payload per call. | (a) Module-level fixture constants. (b) A second literal per edge case. | An edge case is then one mutated or omitted field away from the happy path, and no test can leak a mutation into another. (a) shares mutable state across tests; (b) duplicates the shape, which is how a fixture and its schema drift apart. | A caller can override a field into a shape production would never produce. Bounded by the schema suite validating the unmodified factory output. |
