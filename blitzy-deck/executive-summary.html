Part two

Two authorised production changes

Both exist only so the application can start. Everything else was left alone.

Scope control

Change was deliberately contained

Both changes exist only so the application can start under test. Everything else was tested exactly as it is.

What changed Why it was unavoidable Business risk
One combined route file became a folder of separate modules The application could not start, and that file did not even compile None. No new features were added, and the framework connects them by name, so behaviour is unchanged
Four configuration entries were given safe, empty defaults The product reads them while running but never declared them None. No existing setting had its name or its value altered

Part five

Known limits, managed openly

Each limit is pinned down as today's behaviour and recorded for the backlog.

Documented limits

What cannot be tested, and why

These are product gaps, not test gaps. Closing them would mean building features this engagement deliberately did not build.

Limit Cause How it is handled
Several screens cannot open The shared helpers they rely on were never published in the product code Test written, then skipped with a stated reason
Tweet cards never appear The card itself does not exist anywhere in the product Today's behaviour pinned down, gap recorded
One record lookup always errors The data model has no identifier, so its "not found" path can never be reached The real outcome pinned down instead
Charts never draw The charting engine is never switched on The handled-failure path pinned down; the screen stays usable
The product reports nothing about its own health No live metrics or request tracing, and the health probes point at an address that does not exist Recorded and put on the backlog, not built
