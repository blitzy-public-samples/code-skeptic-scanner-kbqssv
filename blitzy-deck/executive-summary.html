Part two

Two authorised production changes

Both exist so the suite can load the application under test.

Scope control

Change was deliberately contained

Everything else tested unchanged.

Change Why unavoidable Risk
One combined route file became a folder of separate modules The application could not start, and that file did not even compile No behaviour change: no new features, and the framework connects them by name. Two reading risks are on record — three of the four modules are empty and could be mistaken for a place to add endpoints, and the reordered parameters could be mistaken for a changed interface
Four configuration entries were given the narrowest safe defaults The product reads them while running but never declared them No existing setting had its name or value altered. One risk is on record: the permitted-origins list now defaults to empty, so an unconfigured deployment permits none — narrower than today, where it crashes instead

Part four

Proof, not promises

Enforced by the tooling, and shown by deliberate failure.

Enforcement and reporting

The pipeline now enforces the standard

The 90% bar is the client's own acceptance criterion. Reused: both coverage uploads, labels unchanged. Added: machine-readable results, kept as downloads, and a readiness check. Two pre-existing checks, outside this work, still halt the first job.

Runners fail the build below each bar; two pre-existing lint steps fail ahead of them.
